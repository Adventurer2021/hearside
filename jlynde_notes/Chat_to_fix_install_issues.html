Enabling unprivileged user namespaces (kernel.unprivileged_userns_clone=1) carries real security trade-offs. Here's what you need to know to decide.

## The risks

1. Expanded kernel attack surface for local privilege escalation
User namespaces expose a large amount of kernel code paths to unprivileged users — namespace setup, UID/GID mappings, mount operations inside the namespace, network namespace creation, and more. Historically, this has been a frequent source of local privilege escalation vulnerabilities. Many kernel exploits chain user namespace creation with another bug to escalate from an unprivileged user to root. Examples include CVEs like CVE-2022-25636, CVE-2022-0492, and others.

2. Sandbox escape potential
If a vulnerability exists in bwrap itself or in the kernel's handling of user+network namespaces, a malicious process inside the sandbox might escape it. Since speakers.sh runs pyannote (which processes your audio), a compromise there could theoretically expose your call audio.

3. Interaction with setuid binaries
On some systems, user namespaces combined with certain setuid binaries or misconfigured services have enabled privilege escalation. The risk depends heavily on your specific distro, kernel version, and installed software.

## Why distributions disagree

- Ubuntu/Debian: Disable by default (kernel.unprivileged_userns_clone=0) because of these risks.
- Fedora/RHEL: Often enable by default but with additional mitigations (seccomp, SELinux).
- Some security-hardened systems: Keep them disabled permanently.
